受管安装在 TLS 入口后配置网页网关。网页网关核验登录、应用入口权限和旅行分享权限；将原始应用端口和核心后端端口限制在回环地址。[统一登录](UNIFIED-LOGIN.md)

既有安装读取私有存储配置登记的实际绑定。迁移前先确认 workspace 与唯一写入者。新主机使用已核验的恢复文件，空白演示不能覆盖注册数据。

私有数据、凭据、开发机 node_modules、Git 元数据与无关项目均不进入镜像。`.dockerignore` 使用默认拒绝、逐项放行的上下文；TingProof 数据库、Slides decks/.lattice 永不上传到构建上下文。Travel 路线属于应用源码，构建后随镜像版本更新。

## 准备与日常命令

使用 Docker Engine、Compose v2 和 Node 22.16 或更高版本。按 UID/GID 配置非 root 应用及绑定目录的权限。以拥有部署配置的账号从控制仓根目录调用。

服务组、镜像 ID、绝对挂载和启用的服务由安装方的私有描述文件指定。基础应用、核心后端和存储分别核对；两个路由服务和四个槽位由蓝绿控制器管理。

```sh
node scripts/managed-compose.mjs check apps
node scripts/managed-compose.mjs status apps
node scripts/managed-compose.mjs status core

node scripts/managed-compose.mjs status storage
npm run deploy -- status
```

平台后端统一称为 `core`。受管命令兼容既有描述文件中的 `business` 组，保留原项目名、配置路径和数据绑定。

启动前检查活动 writer、非空注册数据、目录权限和端口。应用组与核心后端组避免重复启动同一 writer。镜像和注册绑定一致后再检查页面与媒体功能。停止服务时保留目录、卷和检查点。

私有 Compose 描述及其引用的配置均放在容器不可写目录。对单文件只读挂载进行原子替换可能留下旧 inode，轮换后重建消费服务并核验容器内实际内容。

下列应用配置记录了服务端合同及早期统一启动器所生成的绑定。当前受管部署应在私有 Compose 文件中声明具体挂载与应用环境变量，各固定版本的应用文档列出其支持的参数。

Travel地图凭据可选放在`~/.config/praxis/secrets/travel-amap.json`（文件600、父目录700），或通过`PRAXIS_TRAVEL_AMAP_CONFIG`指定外部绝对路径。统一栈只生成包含文件路径的私有`compose.travel-map.json`，将该单一文件只读挂到Travel的`/run/secrets/travel-amap.json`，不挂整个秘密目录，不复制密钥到环境、源码或镜像。文件格式为`{"key":"JS API Key","securityJsCode":"安全密钥"}`；未配置时仍能启动并阅读行程。独立Travel使用`TRAVEL_AMAP_CONFIG`指向同格式文件；更换凭据后只需重启Travel。当前测试凭据有效期较短，服务健康不代表提供方额度与凭据长期有效。

v0.1.36起，同一配置可增加可选`webServiceKey`，专用于Travel服务器的高德Web服务查询；与JS Key独立，不出现在客户端地图配置。沿用原单文件只读挂载，不新增秘密目录挂载或平台设置页面。用户提供的是测试Key，准确有效期及长期额度未作保证。

v0.1.38的Travel业务模式在`business.json`配置`apps.travel`，固定适配器`http://127.0.0.1:4323/api/business`、一个攻略空间、`keyFile`、`dataDir`与`businessConfigFile`。`dataDir`必须与`appSources`登记的`travel/itineraries`目录一致且预先存在、权限700；签名Key和攻略空间映射分别为Git外600文件、父目录700。映射格式为`{"version":1,"webSpace":"空间ID","spaces":{"空间ID":["western-sichuan-2026"]}}`。栈仅将数据目录可写挂到`/data/itineraries`，两个配置文件分别只读挂载；首次网页读取不创建记录，首次授权MCP更新才生成私有攻略。损坏版本失败关闭，不回退旧内容。只处理共同阅读的非敏感攻略，不据此宣称网页租户隔离。

飞猪测试Key独立放在`~/.config/praxis/secrets/travel-fliggy.json`（600、父目录700），格式`{"apiKey":"测试Key"}`；可用`PRAXIS_TRAVEL_FLIGGY_CONFIG`指定外部绝对路径。统一栈只将该文件只读挂到Travel的`/run/secrets/travel-fliggy.json`，设置`TRAVEL_FLIGGY_CONFIG`为此路径；不挂整个秘密目录，不把Key复制到Compose环境或镜像。使用固定版本官方客户端处理签名协议，运行时不安装依赖。酒店、机票、火车与餐饮查询仅通过受限业务MCP提供，不新增网页公共查询入口，也不支持预订或付款。业务写接口只允许指定地点的类型化时长、开放时间和价格，整份攻略替换不再支持。更换凭据后重建Travel容器；Key可用性及提供方结果与服务健康分别核验。

存储工作器使用独立服务组，逐项声明读写边界。修改登记或实际位置后重新核对工作器内的绑定。

## Lattice单仓与私有内容

v0.1.63将应用与引擎合并到`third_party/lattice`，`packages/runtime`和`packages/cli`仍提供原生模板／制作／渲染，应用从仓库根目录启动。已有应用ID与`/apps/slides/`地址不变，显示名为Lattice。实际legacy `decks`与`.lattice`已移到私有`apps/lattice-native/`，新业务JSON仍在原`apps/slides-business/`；具体绝对路径以`storage.json`登记为准。旧仓历史同时保存在合并历史和私有恢复bundle，旧源码目录不再参与运行。`.lattice`运行记录从新仓索引排除，不随镜像或新提交发布。

原生配音／观众使用的已有公共模型缓存可通过`business.json`的`apps.slides.modelCaches`指定`piper/tts/asr`三个精确目录。只向业务服务分别只读挂到`/opt/lattice-model-cache/<kind>`，设置对应`LATTICE_PIPER_DIR/LATTICE_TTS_CACHE/LATTICE_ASR_CACHE`；不挂整个HOME／`.cache`、agent配置或提供方凭据。缓存必须canonical、当前用户拥有且无组／其他用户写权限；只允许留在该缓存树内的模型库链接。没有资源时目录与执行结果准确报告前提不足，不自动下载模型或安装agent harness。观众外部模型供应方仍使用原生服务端配置，不能由业务参数指定命令或凭据。

通用 Slides 镜像只包含引擎、应用代码和构建依赖，不包含实际 decks。镜像构建时安装 Chromium、FFmpeg、原生依赖与中英文字体。挂载的源 deck 继续由本地 Lattice portal 实时读取；它保留原来的源文件编辑与开发模块服务，其他应用使用生产服务器。

公开 viewer 把 deck 源码打包进 JavaScript，因此在镜像构建后运行一次独立资产任务，把结果保存在挂载的 `.lattice/runtime/{viewer,workbench}`；这不是启动时安装依赖。`up` 自动完成此步骤。Agent 改动 deck 后运行：

通过所属应用的构建命令生成派生资源。对运行中的服务采用维护窗口，并用合成文稿验证导出。

构建失败时不会启动新的公开服务，也不改写源 deck。更新运行中公开资产应在维护窗口执行，避免读到正在替换的 bundle。Slides 容器有 Chromium 所需共享内存，缓存、生成音视频和 authoring 状态保存在完整 `.lattice`；页面健康只证明门户可访问，视频导出仍应单独验证 `lattice video doctor` 和一个合成 deck 的截图/渲染。

## 首次切换与回退

1. 保持现有入口，先构建镜像并用合成数据验收，核对候选挂载与实际注册来源。
2. 在无网络、非 root、只读环境对 TingProof 的一致性副本执行 schema 预检。不认识的格式单独评审迁移。
3. 停止占用同一端口的旧监听器和写入者，保留原数据且只启用一个 writer。
4. 核对实际应用、核心后端、存储服务的健康状态。分别验收页面、媒体、授权和备份。业务验收由独立受限客户端完成，维护者只读验收摘要。
5. 通过私有描述文件和蓝绿控制器管理各组。限制运行日志大小；存储健康、远端复制和试恢复分别报告。

回退先停止 Docker 各组，确认原生程序兼容当前 schema，再对同一 canonical 数据目录启动原生服务。不得恢复旧目录覆盖较新的业务记录。需要搬迁目录或执行 schema 迁移时，另走授权的恢复/迁移流程；基础设施切换不授权维护者改业务记录。

## 后台存储工作器

`compose.storage.yaml` 与 `Dockerfile.storage` 提供独立的存储服务定义。CPU 镜像固定 restic/rclone 版本并校验下载内容，只有登记的活动写设备可发布快照。

配置和凭据只读，源码仓和应用数据源逐项只读挂载，协调状态和本地备份仓可写。路径或单文件 inode 改变后，按私有描述重新创建受影响的工作器并核验真实挂载。

健康检查校验配置指纹、进程及心跳，给首轮操作留出启动时间；云端未配置或失败时保留待同步状态。成功的本地心跳和远端成功复制各有独立收据。

工作器补充实测：同一隔离 Docker 环境中验证 JSON、父/子 Git bundle、SQLite 停机后无 WAL/SHM 的实际只读挂载、完整 encrypted check 与试恢复；源数据库哈希不变、未创建源端 sidecar。当前镜像还验证取消在途子进程时等待清理，活动协调锁期间停止工作器0.319秒退出、协调锁和 restic 锁均清除。真实云凭据未用于测试。

v0.1.14 文档阶段历史记录：按 PRD F30 分离维护与业务执行者；当时未执行部署或数据迁移。后续已获授权部署，仍不能借切换或测试直接改真实业务记录。Docker、业务 API/MCP、Paseo Codex、手机 App 分别记账，见 [验证方案](VERIFICATION.md)。

v0.1.17 的部署验收检查终端关闭后服务仍运行、服务器数据在重启后保持、应用／业务／存储各组有独立健康记录。历史测试数量见[验证台账](VERIFICATION.md)。

## Projects与双通道入口

Projects是`third_party/projects`独立子模块，全部项目共用一个4327服务。统一业务组配置`apps.projects`：固定`http://127.0.0.1:4327/api/business`、`managed:true`、独立`keyFile`、`dataDir`与`businessConfigFile`；映射为`{"version":1,"spaces":["获准空间ID"]}`。配置和密钥为Git外600文件，数据目录700；容器只可写该目录，其余只读。受管网页通过统一业务API逐项目鉴权，原始数据GET关闭。具体项目、工作项和资料引用通过受限MCP写入，不进入仓库或镜像。

入口传输由安装方配置。在变更公开 TLS 入口或受信中继前核对证书、固定上游和转发边界，再检查受保护路由。个人网络拓扑、凭据和路由清单由安装方私有保管。

## 蓝绿发布（v0.1.71）

Praxis 网页入口 `14321` 和核心后端 API／MCP 入口 `4326` 使用稳定转发容器，蓝、绿版本分别运行在 `24321/24326`、`34321/34326`。登录、工作台、管理、PRD 和 MCP 随核心版本一起切换。业务应用、渲染作业和存储工作器保持单实例，继续使用原来的 JSON、SQLite 和命名卷；本版不把这些独立进程双开。现有 `4321` 本地应用入口保持不变，认证工作台仍由核心提供。

首次接入（需要已有 Docker 栈运行）：

```sh
npm run deploy -- init
```

首次接入需要把原来的两个监听进程换成转发容器，有一次短暂交接。后续发布、查看与回滚：

```sh
npm run deploy -- deploy
npm run deploy -- status
npm run deploy -- rollback
```

`deploy` 从当前源码构建候选镜像，也可用 `--image IMAGE` 指定镜像；部署记录固定为镜像 ID，避免可变标签破坏回滚。候选网页和未激活核心先检查就绪，再暂停新请求、排空已有请求、关闭旧核心数据库及采集器、转移唯一写入租约，最后恢复两个入口。等待中的请求最多排队 30 秒，超过限制返回 `503` 和 `Retry-After`，不会重放 POST。GET 事件流和 WebSocket 在交接时关闭，由客户端重连；正在执行的 POST 会等待完成。候选检查失败时原版继续服务；交接失败会尝试恢复原版。

早期版本曾使用独立来源，冷连接下可能发生 TLS 握手问题。移到工作台的受保护路径后，在新浏览器来源需要重新授权并验证 Matrix 设备。

回滚只切换代码和路由，**不回退业务数据**。发布必须保持已有数据格式可读写；涉及不兼容数据格式的版本不适用这套在线回滚。

私有控制目录默认为 `~/.config/praxis/deployment/`，目录 `700`、文件 `600`，不进 Git。`manifest.json` 记录镜像、活动版本和上一版，`state/state.json` 原子更新两个入口及写入者，Unix socket 提供本机排空控制；独立 `lease/` 目录限制核心只有一个写入者。只读候选核心不打开 Auth／Events 数据库、不启动采集器。部署命令用独占锁防止两次发布并行。

单例应用和存储由各自的受管服务组处理。单独暂停／恢复核心用 `npm run deploy -- down` 和 `npm run deploy -- up`。已健康的 `up` 不重建容器。更换控制目录时设置 `--state-dir PATH`。

发布进程异常退出后，确认原进程已不存在的锁可自动回收；活跃、损坏或其他用户的锁会拒绝接管。若退出发生在路由更新与发布记录提交之间，状态会显示 `needsRecovery`，阻止误删正在服务的版本；执行 `npm run deploy -- up` 恢复已记录版本，再发布。候选或交接失败的代码与时间写入私有发布记录，不含运行环境凭据。

2026-11-16 的发布验证记录了首次就绪失败时恢复原核心，修正后完成蓝绿切换与回退。连续 284 次请求成功，最大观测响应 348 ms。合成测试另覆盖在途写入恰好一次、断连排空、会话／OAuth／事件保持、坏候选及异常退出锁恢复。

Memo 指南由同一 4325 服务提供。`apps.memo` 固定适配器为 `http://127.0.0.1:4325/api/business`，配置独立 `dataDir`、`keyFile` 和显式 `spaces`；应用栈校验后仅挂载指南目录与只读签名密钥，通过 `MEMO_DATA_DIR`、`MEMO_BUSINESS_KEY_FILE`、`MEMO_SPACE_IDS` 传入。未授权请求不能读取托管指南；本机照片、凭证和计时继续保留于浏览器，不属于这个服务端目录。

## Polaris 只读查看器

现行独立发行采用查看器与固定目标入口，在 `/apps/polaris/` 由受管网关核验平台管理员身份。数据服务读取工作区匹配的只读观察文件。隔离网络、单文件挂载和替换后的核验见[查看器手册](POLARIS-VIEWER.md)。
## Intelligence展示预览

Intelligence 的受保护入口为 `/apps/intelligence/`。预览模式只读合成资料，真实模式使用显式数据目录。工作台与管理页应区分这两种状态。

应用根遵守`workingData.roots.intelligence`覆盖规则，正式模式只读挂到`/data/intelligence`并读取`data.json`；目录／文件缺失拒绝启用，不自动建库或用预览回退。真实资料与采集／业务MCP按后续合同接入。管理页依据受信容器元数据区分预览来源和正式绑定，不将空工作目录声称为活动数据源。

### Letters 和 Profiles

网页槽在 `/apps/letters/`、`/apps/profiles/` 提供阅读界面。应用源码可公开，文件目录、名称和正文均为私有数据。仅配置的所有者使用自己的原生 Praxis 会话且有平台管理员身份时可访问。

在部署控制目录建立权限 0600 的私有 `private-documents.json`。字段 `ownerId` 填所有者固定 Praxis 用户 ID，`letters`、`profiles` 填两个独立且无符号链接的绝对目录。蓝绿控制器只向网页槽提供只读挂载。未配置时不提供资料访问。合成资料用于发布验收。真实文件、清单、备份及旧主仓历史不作为公开代码仓的发布来源。

首次发布验收从空目录开始，再分别从工作台进入两个应用、阅读合成文档，并在桌面及 390 像素视口通过小房子返回。首次发布前的旧槽没有这两个图标，应用地址返回 404。回滚到该槽后恢复旧入口状态，宿主机上的原件保留。
